# Класифікація проєкту та аналіз його оточення — InteresMe

## 1. Класифікація проєкту

| Ознака класифікації | Обрана категорія | Обґрунтування |
| -------------------- | ------------------ | -------------- |
| Розмір проєкту | Середній | InteresMe вже включає фронтенд, бекенд, базу даних, автентифікацію, а також модулі стрічки, чату, пошуку, каталогу інтересів та ініціатив, що виходить за межі невеликого CRUD-застосунку. Водночас проєкт розробляється одним учасником і поки не має організаційного масштабу великої комерційної платформи, тому категорія "Середній" є найбільш точною. |
| Тип продукту | Вебзастосунок | Продукт реалізований як вебплатформа: фронтенд на Angular взаємодіє з бекенд API на ASP.NET Core через HTTP, а дані зберігаються в PostgreSQL. Це класична архітектура клієнт-серверного вебзастосунку без нативних мобільних клієнтів на поточному етапі. |
| Галузь застосування | Інше — соціальні платформи / social discovery | InteresMe зосереджений на пошуку людей, спільнот та ініціатив за інтересами, цілями, навичками й активностями, тобто належить до сфери соціальних платформ (social discovery), а не до окремої галузі на кшталт освіти чи фінансів. Використання репозиторію для навчального завдання не змінює галузь самого продукту — освітній контекст стосується лише документації, а не призначення платформи. |
| Рівень невизначеності вимог | Високий | InteresMe — це продуктова, стартап-орієнтована ідея, для якої немає заздалегідь зафіксованого повного переліку вимог від замовника. Поведінка користувачів, ефективність механізму рекомендацій, затребувана функціональність спільнот та оптимальна модель взаємодії ще потребують перевірки на реальному використанні та відгуках, тому рівень невизначеності вимог оцінюється як високий. |
| Модель співпраці | Стартап | Продукт розробляється як незалежна ініціатива автора, а не на замовлення конкретного зовнішнього клієнта з фіксованим технічним завданням. Рішення щодо функціональності та пріоритетів приймає сам розробник на основі власного бачення продукту, що є типовою ознакою стартап-моделі, а не аутсорс/замовної розробки. |
| Тип життєвого циклу | Гнучкий (Agile) | Високий рівень невизначеності вимог, потреба в поступовому уточненні функціональності та вже наявна історія інкрементальних релізів (окремі модулі додавались поступово, комітами за напрямками) роблять Agile суттєво доречнішим за жорсткий Waterfall-підхід із заздалегідь повністю зафіксованими вимогами. На практиці розробка також має ітеративно-інкрементальні риси (функціональність нарощується частинами й уточнюється за результатами використання), однак як єдина обрана категорія в таблиці визначено саме Agile. |

## 2. Аналіз внутрішнього оточення

- **Склад і компетенції команди**
  - Проєкт наразі розробляється одноосібно Максимом, який виконує всі ролі: Project Manager / Team Lead, Product Owner, Developer, Designer, Analyst.
  - Перевага такого підходу — швидке прийняття рішень і прямий контроль над продуктовими та технічними рішеннями без потреби узгоджувати кожен крок з іншими учасниками.
  - Слабка сторона — сильна залежність від однієї людини (bus factor = 1), обмежена здатність вести кілька напрямків розробки паралельно, а також ризик перевантаження та частого перемикання контексту між ролями (аналіз, дизайн, розробка бекенду й фронтенду одночасно).

- **Технічні ресурси**
  - Робочий комп'ютер/ноутбук розробника, система контролю версій Git та репозиторій на GitHub.
  - Бекенд-стек: ASP.NET Core / .NET, PostgreSQL, Entity Framework Core, Swagger/OpenAPI для документування API.
  - Фронтенд-стек: Angular, TypeScript, Node.js/npm.
  - Docker та docker-compose для контейнеризації та локального запуску всієї системи.
  - Редактор коду / IDE для розробки.
  - У репозиторії вже налаштований CI (GitHub Actions) для автоматичної збірки бекенду та фронтенду при змінах у `main`.
  - Більшість використаних технологій — відкриті (open-source) або доступні без істотних витрат на ліцензування на поточному етапі; окремих платних корпоративних ліцензій проєкт не потребує.

- **Часовий бюджет**
  - Плановий бюджет часу на поточному етапі — приблизно **15–20 годин на тиждень**.
  - Це орієнтовна планова оцінка доступного часу для розробки, а не виміряна історична статистика витраченого часу.
  - Реальний обсяг може змінюватись залежно від навчального навантаження та інших зобов'язань розробника.

- **Досвід з тематикою**
  - Розробник має практичний досвід роботи з технологіями, які вже використані в репозиторії: ASP.NET Core, Angular, PostgreSQL, побудова REST API, автентифікація (JWT, OAuth), Docker, Git, а також інтеграція фронтенду й бекенду.
  - Щодо предметної області (social discovery), продуктові гіпотези — зокрема цінність механізму підбору за інтересами та затребуваність спільнот — ще потребують перевірки на реальних користувачах; глибокого досвіду саме в побудові подібних соціальних платформ поки не накопичено.

- **Організаційне середовище**
  - Проєкт розробляється незалежно, без зовнішньої організації чи замовника.
  - GitHub використовується як центральний репозиторій вихідного коду та джерело документації (README, проєктні документи).
  - Той самий репозиторій також використовується як основа для навчальних робіт із курсу з управління проєктами; навчальні вимоги задають окремі документаційні етапи (лабораторні роботи), але не визначають фактичну продуктову дорожню карту InteresMe.
  - Наслідком одноосібної розробки та відсутності формальної організаційної структури є легковажний (lightweight) процес прийняття рішень: рішення приймаються швидко, без формальних погоджень, що пришвидшує розробку, але водночас підвищує ризик відсутності незалежної перевірки рішень.

## 3. Аналіз зовнішнього оточення

### Цільова аудиторія та її потреби

Основна аудиторія відповідно до `project-brief.md`: молодь, студенти, молоді спеціалісти, розробники, автори контенту та учасники спільнот і проєктних команд, орієнтовно віком **16–35 років**.

Ключові потреби цієї аудиторії:
- знаходити релевантних людей поза межами наявного соціального графа;
- знаходити людей із сумісними інтересами, цілями чи навичками;
- приєднуватися до проєктів або ініціатив;
- відкривати для себе спільноти за інтересами;
- спілкуватися з релевантними людьми після їх знаходження;
- скорочувати час, витрачений на пошук серед розрізнених чатів, груп та платформ.

### Аналоги та конкуренти

**Meetup** — платформа, орієнтована на пошук груп, подій та людей за спільними інтересами.
- Спільне з InteresMe: пошук за спільними інтересами, наявність спільнот, побудова соціальних зв'язків.
- Відмінність: InteresMe робить більший акцент на індивідуальному профілі користувача — цілях, навичках, проєктах та ініціативах — і на прямій релевантності між конкретними користувачами, тоді як Meetup історично зосереджений передусім на пошуку подій і груп, а не на індивідуальному підборі людей.

**Bumble For Friends (BFF)** — продукт, орієнтований на дружні (платонічні) знайомства та пошук нових людей.
- Спільне з InteresMe: пошук нових людей, врахування інтересів, розширення кола спілкування.
- Відмінність: InteresMe покриває ширший контекст, ніж лише дружба — включно з пошуком людей для спільних проєктів, навичок, ініціатив і спільнот на основі цілей, а не тільки платонічного знайомства.

Наведені описи ґрунтуються на загальновідомому позиціонуванні цих продуктів; точні дані про кількість користувачів, дохід чи алгоритми цих сервісів у цьому документі не наводяться й не стверджуються.

### Технологічні тренди

- Персоналізовані системи рекомендацій як стандартний очікуваний елемент сучасних соціальних продуктів.
- Пошук за інтересами та підходи, що спираються на графи зв'язків (interest-based / graph-based discovery).
- Обмін повідомленнями в реальному часі (real-time messaging).
- Автентифікація через OAuth і соціальний вхід (Google, GitHub тощо) як звичний стандарт для зменшення бар'єру входу.
- Mobile-first та адаптивні вебінтерфейси.
- Принцип "приватність і безпека за замовчуванням" (privacy and security by design).
- Модерація контенту та механізми довіри й безпеки (trust & safety) для соціальних платформ.
- Зростаюче очікування користувачів щодо персоналізованих стрічок і релевантного пошуку контенту/людей.

Важливо зазначити: сучасна версія InteresMe не претендує на використання складних алгоритмів штучного інтелекту чи машинного навчання — наявний функціонал підбору базується на явних даних профілю (інтереси, каталог), а не на просунутих ML-моделях.

### Регуляторні та правові чинники

Оскільки InteresMe працює з персональними даними користувачів та контентом, який вони створюють, у міру росту продукту слід враховувати такі фактори (без надання юридичної консультації, лише як перелік аспектів для подальшого розгляду):

- обробка персональних даних користувачів;
- наявність політики конфіденційності (privacy policy);
- отримання згоди користувача на обробку даних;
- можливість видалення акаунта та пов'язаних даних;
- безпечне зберігання автентифікаційних даних (паролі, токени);
- порядок поводження з контентом, згенерованим користувачами;
- механізми модерації та подання скарг на зловживання;
- відповідальність за авторські права на контент, завантажений користувачами;
- можлива застосовність GDPR у разі обслуговування користувачів у Європейському Союзі.

### Партнерські системи та API

На основі фактичної документації репозиторію InteresMe залежить від таких зовнішніх систем:
- **Google OAuth** — для входу через обліковий запис Google;
- **GitHub OAuth** — для входу через обліковий запис GitHub;
- **PostgreSQL** — як інфраструктурна залежність для зберігання даних;
- **GitHub / GitHub Actions** — як центральний репозиторій коду та платформа CI, що вже налаштована в проєкті.

Використання зовнішніх OAuth-провайдерів створює залежність від їхньої доступності та конфігурації (наприклад, налаштування client ID/secret, дозволених callback-адрес); недоступність чи зміна конфігурації цих провайдерів може тимчасово обмежити спосіб входу користувачів у систему.

## 5. Висновки

Обрана класифікація — середній за розміром стартап-проєкт із високим рівнем невизначеності вимог — напряму визначає доцільність гнучкої (Agile) методології розробки. Оскільки остаточна цінність механізму discovery, найкраща модель спільнот і навіть пріоритетність окремих модулів (чат, ініціативи, каталог інтересів) стануть зрозумілими лише після взаємодії з реальними користувачами, жорсткий Waterfall-підхід із повністю зафіксованими на старті вимогами був би погано пристосований до InteresMe: будь-яка суттєва зміна вимог після завершення "аналізу" в такій моделі коштувала б надто дорого. Натомість ітеративно-інкрементальна розробка, коли функціональність постачається окремими модулями та уточнюється за результатами використання, відповідає і фактичній історії розвитку репозиторію (модулі Auth, Profile, Posts, Chat, Discovery, Interests, Initiatives додавались поступово), і природі стартап-моделі співпраці.

Серед найбільш критичних факторів середовища, виявлених в аналізі, варто виділити: одноосібну команду (bus factor = 1) з обмеженим часовим бюджетом 15–20 годин на тиждень; необхідність перевірки продуктових гіпотез на реальних користувачах, оскільки наразі значна частина цінності продукту спирається на неперевірені припущення; конкуренцію з боку зрілих соціальних платформ (зокрема Meetup та Bumble For Friends), які вже мають налагоджені механізми пошуку людей за інтересами; вимоги до приватності, безпеки та довіри, обов'язкові для будь-якої соціальної платформи, що працює з персональними даними та контентом користувачів; а також залежність цінності самого продукту від мережевого ефекту — платформа discovery корисна лише за наявності достатньої активності користувачів.

Із цього випливає низка передбачуваних ризиків на ранньому етапі. По-перше, ризик перевантаження єдиного розробника та вповільнення прогресу через необхідність поєднувати всі ролі одночасно. По-друге, ризик того, що продуктові гіпотези виявляться хибними без структурованої перевірки на користувачах, що призведе до витрати часу на нерелевантну функціональність. По-третє, ризик надмірного розширення функціонального обсягу (scope creep) — прагнення одразу реалізувати повний набір соціальних функцій замість фокусування на ключовому MVP. По-четверте, ризик слабкої цінності механізму discovery за низької початкової активності користувачів, оскільки соціальні платформи такого типу залежать від "критичної маси" контенту та профілів. Також залишаються реальними, хоча наразі не критичними, ризики, пов'язані з модерацією, зловживаннями та безпекою даних, а також залежність від доступності зовнішніх OAuth-провайдерів. Жоден із цих ризиків не применшується, але наразі жоден із них не є ознакою кризи проєкту — це очікувані ризики для продукту на цій стадії.

Виходячи з цього, доцільними подальшими кроками є: чітке визначення обсягу MVP із пріоритетом на ключові потоки — профіль, discovery та чат — як основу цінності продукту; перевірка ключових продуктових гіпотез на реальних цільових користувачах перед подальшим розширенням функціональності; збір структурованого зворотного зв'язку та ведення пріоритезованого беклогу задач; робота короткими ітераціями з регулярним переглядом пріоритетів відповідно до Agile-підходу; посилення тестового покриття та уваги до безпеки (особливо автентифікації та зберігання даних); визначення базових вимог до приватності й модерації до відкриття продукту для ширшої аудиторії; а також системне відстеження ризиків і припущень, зафіксованих у цьому документі, у подальшій проєктно-управлінській роботі над InteresMe.
